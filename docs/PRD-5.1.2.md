## 1. 产品目标与本版主题

**一句话产品目标**：让「预警读得到、通知收得到、时间看得全、AI 答得准、组件调得动」——把 5 条用户抱怨收敛成一次可验收的体验补齐。

**本版主题**：**「把看不见的状态变成看得见的状态」**。5 条需求里有 3 条（R1 预警读取、R3 结束时间、R5 组件状态）本质是同一类问题：系统知道，但界面没说；另外 2 条（R2 推送、R4 AI 能力）是把已有后端能力真正接到用户面前。

三个正交目标：

| # | 目标 | 衡量口径 |
|---|---|---|
| G1 | **可信**：预警与红石信息在任何网络/数据状态下都给出确定、不误导的表述 | 不再出现「读不到」的首帧、不再需要心算结束时间 |
| G2 | **可达**：关键信息在用户不在 App 内时也能送达 | 预警通知到达率、可配置率 |
| G3 | **可控**：AI 与小组件的能力/状态都能由用户或验收者显式控制 | 开关覆盖率、调试面板可枚举覆盖率 |

### 1.1 现状核实（PM 判读，仅列影响产品决策的事实）

- **R1**：真正读取预警的是 `SkyRoomView.swift`（`@ObservedObject AlertStore.shared`，`alertsBlock` 三态渲染，`refreshPolledData()` 以 `force: false` 起一次刷新）。页面是 `fullScreenCover`，**每次进场视图身份新建、`@State` 归零**；`AlertStore` 虽是跨页面单例，但结果只在内存、无持久化。首帧在请求回来前必然落到 `SkyRoomAlertStatusRow(.unknown)` → 用户看到的「预警数据暂时取不到」。同时「没配 key / 上游挂了（`ok==false`）」「传输失败」「还没问」「确实没有预警」四种语义被压成两三种文案，且预警没有自己的「数据来源 / 上次成功时刻」说明 → 用户无法判断 `Endpoint.alertsPath` 这个专门链接到底有没有用。**这是状态语义问题，不是单纯的网络问题。**
- **R2**：`AlertStore` 用的是 `UNUserNotificationCenter` 本地通知，`AlertStore` 文件头已写明：侧载 App 无 APNs 证书，进程挂起后收不到；项目已有整套 Bark 通道（`push_bark_key`、`BARK_API`、`daily-brief.js`、`app-monitor.js`、`settings.js` 脱敏配置），但**没有天气预警推送通道**。
- **R3**：`Occurrence` 已有 `startAt` / `endAt`（= 落地 + 52 分钟）/ `time`，`endAt` 是现成真值；`NextEventBar` 的 `RockPhaseText.headline` 只拼 `occurrence.time`，全页文案口径共用这一份。
- **R4**：现有 `Sources/Features/AIChat/` 五件套 + `AIChatStore` + SSE 后端 `/api/ai/chat.js`（`buildSystemPrompt`「大肥鱼」人格）；已有 `SpeechStore` + `/api/app/tts`（24h 预签名直链、AVPlayer），但**朗读入口未全量覆盖消息**，**无联网搜索、无引用展示**。`AIChatComposer` 目前只有输入框 + 发送/停止，没有能力开关行。
- **R5**：`SkyWidgetBundle` 注册 8 个组件、多尺寸 family；`WidgetProvider` 管 Timeline/entry；`*Face` 是渲染层。`MoreView` 分「工具」「其他」两组，`SettingsView` 是 sheet。**`docs/DESIGN-RULES.md` §4「交互入口单一」明确禁止多处挂同一目标** —— 这是需求5 入口歧义的裁决依据。

## 2. 逐条需求：用户故事与验收标准

### R1 · 天光页预警「读不到 / 每次重新读」

**用户故事**：作为每天打开天光页看天气的用户，我希望一进页面就看到**确定的**预警状态（有预警 / 确认无预警 / 正在读取 / 读取失败），并且不用每次都重新等一次网络，以便我立刻知道今天有没有灾害预警、以及这个预警功能到底是好的还是坏的。

**产品判断（三件事都要，但有主次）**：核心是**「首屏立刻有值 + 状态可区分」**，其次才是缓存。具体预期：① 上次成功结果跨启动保留，进场先渲染它并标注「上次更新于 HH:mm」；② 进场不强制重读，只在数据超过刷新窗口（与后端 5 分钟缓存对齐）时后台静默刷新，显式下拉刷新才强制；③ 状态四分且互斥，**「读取失败」不得冒充「当前无天气预警」**；④ 预警有且只有一条权威数据源，界面给出「用的哪个接口 + 最近一次请求成功/失败 + 时刻」的可诊断信息，直接消灭「不知道专门链接有没有用」。

**验收标准（「修好」判据）**：

- **AC1-1** 杀进程冷启动后首次进入天光页，**1 秒内**出现上述四种状态之一；**首帧不得出现「预警数据暂时取不到」作为默认落地态**。本地有上次成功结果时，直接渲染该结果并带「上次更新于 HH:mm」。
- **AC1-2** 四态互斥、任一时刻只显示一种：① 有预警（横幅 + 四色级别，最多 3 条沿用现状）；② 确认无预警（「当前无天气预警 · HH:mm 更新」）；③ 首次读取中（「正在获取预警…」，**不写「取不到」**）；④ 读取失败（「预警读取失败」+「重试」按钮 + 最近一次成功时刻）。
- **AC1-3** 断网、接口 `ok==false`、请求超时三种情况下，已有预警横幅**不得消失**，必须带「最后更新于」时间戳；三种情况都不得渲染成「当前无天气预警」。
- **AC1-4** 坐标不变、10 分钟内连续进出天光页 10 次，预警请求数 **≤ 2 次**（含回前台那一次），以抓包计数为准；只有下拉刷新 / 切换城市 / 超过刷新窗口才发起新请求。用户主观上不再有「每次打开都在重新读」的观感。
- **AC1-5** 预警区（或其诊断入口）可查看：当前使用的预警接口、最近一次请求结果与时刻、本次是否有缓存兜底；用户据此能判断专门链接是否生效。全 App 预警数据只走这一条源。
- **AC1-6** 后台静默刷新回来后状态平滑切换（③/④ → ①/②），无中间态闪烁、无整页重排；浅色/深色、iPhone/iPad 均通过。
- **AC1-7（前置）** 若上游 key 未配置或长期 `ok==false`，后端需确认其状态；此项不成立时 App 侧只能保证「明确报错」，不能保证「读得到」，见待确认 Q7。

### R2 · 有预警却没有通知（ark 推送）

**用户故事**：作为不会一直开着 App 的用户，我希望有天气预警时手机能直接收到推送通知，以便 App 没打开也不会漏掉暴雨、雷暴这类预警。

**产品判断**：**采用后端 Bark 定时检测 + 推送**，本地通知只保留为「App 在前台时的即时通道」。理由：侧载 App 无 APNs 证书，进程挂起后本地通知必然收不到，用户抱怨的正是这段空窗；Bark 通道、密钥配置、脱敏、监控都已在项目中，复用成本最低。产品必须同时给出**去重、分级、可配置**三件事，否则「每 5 分钟一条暴雨黄色」会逼用户关掉通知。

**验收标准**：

- **AC2-1** App 未启动 / 后台 / 被挂起时，注入一条测试预警后 **10 分钟内**收到 Bark 通知（含类型、级别、发布台站、发布时间）。
- **AC2-2** 同一条预警（`id` 相同）在有效期内**只推一次**；**新增**或**级别升级**（如黄→橙/红）才再推；预警解除默认不推。不得出现同一条预警重复轰炸。
- **AC2-3** 设置中提供「天气预警推送」开关（默认开）、最低推送级别选择（默认「黄色及以上」）、免打扰时段（默认关闭，避免漏报）。配置变更后下次检测即生效。
- **AC2-4** 点击通知深链直达天光页预警区（沿用已有 `skyapp://sky` 深链），不落到首页。
- **AC2-5** Bark 密钥未配置、密钥失效或推送失败时，**不影响 App 内预警显示**；失败记录可在已有「推送监控」中看到，不静默吞掉。
- **AC2-6** 前台时保留现有本地通知即时横幅；两条通道各自按 `id` 去重，同一条预警用户最多各收到一次，不叠加轰炸。

### R3 · 红石只显示降落时间

**用户故事**：作为按红石场次安排游戏时间的用户，我希望每一场都同时看到降落时间和结束时间，以便我知道这一场能打到几点、不用自己心算 52 分钟。

**产品判断**：**所有出现降落时间的位置都要补结束时间**，且结束时间必须取自现成的 `Occurrence.endAt`（= 落地 + 52 分钟），不另算一套。紧凑位置用 `11:08–12:00`，详情位置用「降落 11:08 · 结束 12:00」；跨日场次带「次日」标记。

**验收标准（「修好」判据）**：

- **AC3-1** 顶部「下一场」条在 `upcoming` / `ongoing` / `endedToday` 三种相位均显示结束时间；`notGenerated` 态保持现状，**不出现 `--:--` 之类的假时间**。
- **AC3-2** 红石日历页场次列表、日详情 sheet、今日列中，**每一场**都显示「降落 HH:mm · 结束 HH:mm」，逐处点名验收，一处不漏。
- **AC3-3** 结束时间与 `Occurrence.endAt` 完全一致（抽查含 23:30 → 次日 00:22 的跨日场次，须带「次日」）；全文不出现第二套时长口径。
- **AC3-4** `RedstoneWidget` 小 / 中 / 大及锁屏 / 实时活动中凡显示降落时间处同步显示结束时间；「进行中」态显示「12:00 结束」。
- **AC3-5** 动态字体放大到系统最大档时结束时间不被截断；浅色/深色、iPhone/iPad 四档通过。
- **AC3-6** 顶部条与概览卡的「下一场」文案仍共用同一份口径（现状 `RockPhaseText`），不得出现两个页面说法不一致。

### R4 · DeepSeek 全家桶能力搬进 App

**用户故事**：作为用 AI 查实时信息的用户，我希望 AI 对话能开关联网搜索、看到回答的引用来源，并且每条回答都能朗读，以便答案可以核实、也能边走边听。

**文章要点（引用主理人已抓取内容）**：《DeepSeek 发布全家桶应用 API》（深度求索 2026-11-13）把联网搜索、文件输入、阅读链接、语音交互、安全等整合进 API；`deepseek-flash`（V4.1-Flash）在 Messages / Responses / Chat Completions 下支持 `deepseek_web_search`（带引用）、文件输入（PDF/Office/图片）、`deepseek_read_url`、模型安全；底层 Search / Fetch / OCR / ASR / TTS 可独立调用；官方开源 Demo `https://cdn.deepseek.com/chat-demo`（代码 `https://github.com/deepseek-ai/chat-demo`）可 1:1 复刻完整 App 并支持导入历史对话；扩展能力除 token 费外另收工具调用费。

**产品判断（本期范围）**：**P0 只做「联网搜索开关 + 引用展示 + 朗读全量覆盖」**，即用户原话点名的两件事；页面改版随 P0 同批交付但不做像素级 1:1 复刻（风格见待确认 Q2）；深度思考、文件/读链接、语音输入登记为 P2，本期不做。理由：本项目走自建 `/api/ai/*` 代理，引入联网搜索要动后端参数与计费链路，范围必须与「能力可灰度、成本可关」绑定。

**验收标准**：

- **AC4-1** 输入框上方提供「联网搜索」开关（**默认关**、按会话记忆），开启后本次问答走联网；回答带可点击引用列表（序号 + 标题 + 域名），正文与引用序号对应。
- **AC4-2** 开关关闭时行为与 3.31.0 一致，**不产生工具调用费**；后端可一键关闭联网能力，关闭时 App 端开关置灰并给出说明。
- **AC4-3** 搜索中 / 无结果 / 引用加载失败各有明确状态，不把「没搜到」渲染成「回答完毕」；引用 URL 打开方式沿用 App 既有外链处理。
- **AC4-4** **每一条** AI 回复（含历史会话消息）都有朗读入口，支持播放 / 暂停 / 停止；复用现有 `/api/app/tts`，不引入新音频通道；流式生成中朗读按钮给出明确不可用态，生成完成后可用。
- **AC4-5** 历史会话、模型切换、SSE 流式中断/停止、清空会话等既有行为不回归；「大肥鱼」人格与 weather/earnings 快照上下文保持不变。
- **AC4-6** 新页面视觉沿用 Theme token，浅色/深色、iPhone/iPad 四档通过；页面风格按 Q2 结论落地。

### R5 · 小组件后台控制面板

**用户故事**：作为需要验收/调试小组件的人，我希望有一个调试页面能切换所有组件的样式、尺寸和任意显示状态并注入模拟数据，以便不用等真实数据、不用反复添加 Widget 就能把每种状态看一遍。

**产品判断**：这是一个**「小组件后台控制面板」**，不是设置开关页。必须覆盖：全部 8 个组件 × 各自支持的全部尺寸 × 全部显示状态 × 模拟数据 × Timeline 刷新控制。入口按 `DESIGN-RULES.md` §4 保持唯一（见待确认 Q3）。

**验收标准**：

- **AC5-1** 入口唯一，进入「小组件调试」页；页面标题与「更多 / 设置」的层级关系清晰，不出现两个入口指向同一页。
- **AC5-2** 组件选择器覆盖 `SkyWidgetBundle` 注册的全部 **8 个**：Redstone / Brief / SunEventLiveActivity / DaylightLiveActivity / SkyLight / SunArc / MoonPhase / Wind；新增组件时清单可随之扩展，不写死漏项。
- **AC5-3** 尺寸切换覆盖各组件支持的全部 family（systemSmall / Medium / Large + 锁屏 rect / inline / circular + 实时活动形态）；**不支持的档位置灰并注明原因**，不可选。
- **AC5-4** 状态切换覆盖：有数据 / 无数据 / 加载中 / 错误 / 收官 / 进行中 / 未生成 / 待确认；某组件不适用的状态置灰说明，不得渲染成空壳。
- **AC5-5** 模拟数据支持：内置预设样例、自定义数据注入、指定时刻（时间旅行）预览；预览按所选 family 的真实画布比例渲染。
- **AC5-6** 调试控制提供：刷新 Timeline、重置为真实数据、复制诊断信息（当前 entry / 数据来源 / 下一次刷新时刻）。
- **AC5-7** 调试态**不得污染用户真实小组件数据**：模拟数据只在预览/调试会话内生效，退出页面后真实 Widget 恢复真实数据；界面需明确标注「当前为调试预览」。
- **AC5-8** iPad rail 档布局、浅色/深色、动态字体通过。

## 3. 需求池

**优先级口径**：`P0` = 必须随 5.1.2 发布；`P1` = 随版发布但排在 P0 之后，工期压缩时可只交最小子集；`P2` = 本期不做，仅登记。

| 编号 | 需求 | 优先级 | 涉及端 | 备注（优先级判断） |
|---|---|---|---|---|
| R1 | 天光预警：首屏立刻有值 + 四态可区分 + 缓存与刷新收敛 + 数据源可诊断 | **P0** | App（后端配合确认 key/缓存） | 用户第一抱怨，且是「界面在说谎」，纯 App 侧可修、收益最高 |
| R2 | 天气预警 Bark 推送通道（后端检测 + 去重 + 分级 + 可配置） | **P0** | 后端 + App（设置开关、深链） | 用户明确「根本没通知」；侧载无 APNs，Bark 是唯一可行服务端通道，已有基础设施可复用 |
| R3 | 红石结束时间全量展示（顶部条 / 列表 / 详情 / Widget / 实时活动） | **P0** | App + Widget | `endAt` 已存在，改动最小、判据最清晰，性价比最高，适合与 R1 同批回归 |
| R4a | AI 联网搜索开关 + 引用展示 | **P0** | App + 后端 | 用户点名能力；涉及后端参数与工具调用费，需灰度/成本开关，是本版最大风险项 |
